☠️ Prototype Pollution — Contaminación de Object.prototype
MED
El endpoint POST /api/merge usa una función de deep merge que no filtra la clave __proto__. Al inyectar propiedades en el prototipo base, todos los objetos del proceso quedan afectados.
— Resultado —
🚩 FLAG{prototype_pollution_pwned} — Object.prototype contaminado
Envía exactamente: {"__proto__":{"polluted":"PWNED"}}
La función deepMerge llama a target["__proto__"] que devuelve Object.prototype, no una propiedad propia — así contamina el prototipo global.

Fix: Filtrar __proto__ y constructor en la función de merge.
// VULNERABLE: propaga __proto__ al prototipo base function deepMerge(target, source) { for (const key of Object.keys(source)) { if (typeof source[key] === 'object') { target[key] = target[key] || {}; deepMerge(target[key], source[key]); // target["__proto__"] = Object.prototype! } else { target[key] = source[key]; } } } // FIX: bloquear claves peligrosas if (key === '__proto__' || key === 'constructor' || key === 'prototype') continue;

CRIT

— Resultado —
🚩 FLAG{insecure_deserialize_rce} — Código arbitrario ejecutado

Usa los botones para generar payloads pre-armados.

⚡ Race Condition — Cupón de un solo uso
HIGH
El cupón RACE100 solo debería usarse una vez. El servidor hace CHECK luego UPDATE sin transacción atómica — una ventana de 50ms permite usar el mismo cupón dos veces simultáneamente.
— Respuestas de ambas requests —
🚩 FLAG{race_condition_double_spend} — Cupón usado dos veces
El servidor: 1) SELECT donde used=0, 2) espera 50ms, 3) UPDATE a used=1.
Entre el paso 1 y el 3 hay una ventana de tiempo — dos requests pueden pasar el SELECT antes de que alguna haga el UPDATE.
Fix: Usar transacciones DB o UPDATE ... WHERE used=0 como operación atómica.
// VULNERABLE: check-then-act no atómico db.query('SELECT * FROM coupons WHERE code = ? AND used = 0', [code], (err, rows) => { setTimeout(() => { // ventana de 50ms db.query('UPDATE coupons SET used = 1 WHERE id = ?', [rows[0].id], cb); }, 50); }); // FIX: UPDATE atómico — solo hace efecto si used=0 db.query('UPDATE coupons SET used=1, used_by=? WHERE code=? AND used=0', [user_id, code], (err, result) => { if (result.affectedRows === 0) return res.status(400).json({ error: 'Ya usado' }); });

🔑 Password Reset inseguro — Token predecible
HIGH
El token de reset es el timestamp Unix actual en hexadecimal — predecible por cualquier atacante. Además no tiene expiración. Solicita un reset, adivina el token y cambia la contraseña.
Paso 1 — Solicitar reset (genera token predecible)
— Token generado —
Paso 2 — Confirmar con el token (sin saber la contraseña original)
— Resultado —
🚩 FLAG{reset_token_predictable} — Contraseña del admin cambiada sin autenticación
El token es Math.floor(Date.now()/1000).toString(16) — el timestamp actual en hex.
El paso 1 te lo muestra directamente (en producción va por email, pero un atacante puede pedirlo justo antes que la víctima y adivinar el timestamp).
Fix: Usar crypto.randomBytes(32).toString('hex') y expirar en 15 minutos.
// VULNERABLE: token = timestamp hex, sin expiración const token = Math.floor(Date.now() / 1000).toString(16); // No verifica created_at al confirmar // FIX: token aleatorio + expiración const token = crypto.randomBytes(32).toString('hex'); const expires = new Date(Date.now() + 15 * 60 * 1000); // WHERE token = ? AND expires_at > NOW()
🐌 ReDoS — Regular Expression Denial of Service
MED
El validador de email usa una regex con backtracking exponencial. Un input especialmente construido bloquea el event loop de Node.js durante segundos, dejando el servidor sin responder.
— Tiempo de respuesta —
🚩 FLAG{redos_event_loop_blocked} — Event loop de Node.js bloqueado
El payload es: aaaaaaaaaaaaaaaaaaaaaaaa@a.
La regex intenta todas las combinaciones posibles de grupos — crece exponencialmente.
En Node.js, esto bloquea el event loop completo porque JS es single-threaded.
Fix: Usar una regex lineal o la librería safe-regex para validar tus patrones.
// VULNERABLE: backtracking exponencial const pattern = /^([a-zA-Z0-9_\-\.]+)@((\[[0-9]{1,3}\.){3}|([\w\-]+\.)+)([a-zA-Z]{2,4})$/; pattern.test('aaaaaaaaaaaaaaaaaaaaa@a.'); // O(2^n) // FIX: regex lineal o librería especializada const pattern = /^[^\s@]+@[^\s@]+\.[^\s@]+$/; // O(n)
🛒 Business Logic — Cantidad negativa
MED
El endpoint de órdenes calcula total = precio × cantidad sin validar que la cantidad sea positiva. Una cantidad negativa genera un total negativo — el sistema te "debe" dinero.
— Resultado —
🚩 FLAG{business_logic_negative_charge} — Total negativo generado
Pon cantidad -10 con el producto más caro ($199.99).
Total = $199.99 × -10 = -$1,999.90 — el sistema registra que te debe dinero.
Fix: if (quantity <= 0) return res.status(400).json({error:'Cantidad inválida'});
// VULNERABLE: no valida que quantity > 0 const total = product.price * quantity; // -10 × $199.99 = -$1999.90 db.query('INSERT INTO orders ... VALUES (?, ?, ?, ?, ?)', [..., total]); // FIX: validar en servidor (nunca en cliente) if (!Number.isInteger(quantity) || quantity <= 0 || quantity > 1000) return res.status(400).json({ error: 'Cantidad inválida' });
↩️ CRLF Injection — Inyección de headers HTTP
MED

— Headers de respuesta —
🚩 FLAG{crlf_header_injection} — Header inyectado en la respuesta
Los headers HTTP están separados por \r\n. Inyectar estos caracteres termina el header actual y añade uno nuevo.
Payload: es%0d%0aX-Injected%3a%20pwned%0d%0aSet-Cookie%3a%20admin%3d1
Versiones recientes de Node.js bloquean \r\n en headers — verás el error en la respuesta, lo que también revela la vulnerabilidad.
// VULNERABLE: valor sin sanitizar en header res.setHeader('Set-Cookie', `lang=${lang}; Path=/`); // lang = "es\r\nX-Admin: true" → dos headers separados // FIX: sanitizar o usar API segura const safeLang = lang.replace(/[\r\n]/g, ''); res.cookie('lang', safeLang, { httpOnly: true });

🔀 Verb Tampering — GET evita la autenticación POST
MED
El endpoint admin solo verifica la API key cuando el método es POST. Enviando el mismo request como GET se salta la verificación completamente.
— Respuesta —
🚩 FLAG{verb_tampering_bypass} — Acción admin ejecutada via GET sin autenticación
El handler usa app.all() — acepta cualquier método.
Pero la verificación de API key solo se ejecuta cuando req.method === 'POST'.
Fix: Aplicar middleware de autenticación sin distinción de método.
// VULNERABLE: app.all() + check solo en POST app.all('/api/admin/secret-action', (req, res) => { if (req.method === 'POST') { if (req.headers['x-api-key'] !== 'admin-secret') return res.status(403); } res.json({ success: true }); // GET llega aquí sin pasar el check }); // FIX: autenticar siempre, sin importar el método app.all('/api/admin/secret-action', requireAuth, (req, res) => { ... });

HIGH
